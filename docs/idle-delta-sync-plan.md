# IDLE 按目录增量同步调整方案

- 日期：2026-11-25。
- 状态：已实施并完成本地验证（2026-11-26）；下文保留设计与设计时的检查结论，实施对照见末节。
- 范围：缩小 IDLE 事件的同步范围，完善移动、重连和发送后的目录更新；保留现有 Go + React、JSON/JSONL、单实例部署方式。
- 本方案已替代此前“IDLE 标记、删除和重连统一触发全账号完整对齐”的策略；当前运行规则见开发文档。

## 1. 检查结论

### 1.1 当前 IDLE 触发范围

当前 `internal/mail/idle.go` 将 EXISTS/RECENT 分为新增邮件，将 EXPUNGE、FETCH 及 UIDNEXT/UIDVALIDITY 等通知统一分为需要对齐。

`internal/app/idle.go` 合并事件时仅保存账号级 `quick/full`，没有保存受影响目录、UID 和原始原因。出现 full 标记后创建账号级 reconcile，扫描全部可选择目录。首次建立监听、连接丢失和重连成功都会请求此类任务，本地 MOVE 成功也请求全账号对齐。

因此，单封邮件的已读变化也可能触发全账号扫描；一次断线的断开和恢复可能分别产生对齐任务。已有完整任务执行期间发生的变化会保留，这项防止漏事件的保护必须保留。

当前日志只保留“IDLE 事件触发”，无法区分新邮件、标记变化、目录状态通知或连接补偿；已有启动需求也可能被后来合并的 IDLE 来源覆盖。

### 1.2 发送邮件是否保存到服务器

已核对 `internal/app/app.go` 的 QueueSend/sendJobs、`internal/mail/mail.go` 的 Send/deliver、账号编辑及发件箱界面。

| 阶段/配置 | 当前实际行为 | 本地结果 |
| --- | --- | --- |
| 正常发送 | 通过账号配置的 SMTP 提交 MIME 和收件人 | 服务器最终接受 DATA 后标记 sent，移除关联本地草稿 |
| 默认配置，autoArchive=false | 找到本地已发现的 sent 角色目录，经 IMAP APPEND 写入同一 MIME，并设置已读 | APPEND 成功后 archive=saved |
| 勾选“服务器会自动保存已发送邮件” | 跳过 APPEND，依赖邮件服务自己的保存行为 | 直接设置 archive=server，当前没有验证远端副本是否存在 |
| 未找到已发送目录 | 不创建目录，不执行 APPEND | 邮件仍为已发送，归档失败；可在发现目录后手动重试归档 |
| 归档连接失败 | SMTP 不重发 | archive=failed，界面可重试归档 |
| APPEND 已进入提交阶段后返回错误或进程中断 | 保守视为保存结果不确定 | archive=unknown，禁止自动重放 APPEND |
| SMTP 提交后连接中断，无法确认结果 | 不自动再次发送 | state=unknown，需要人工核对 |

“发送成功”和“已发送副本保存成功”是两个状态。SMTP 接受也不等于收件人最终收到邮件。

当前客户端 APPEND 成功后仅保存任务状态并通知前端，没有主动创建已发送目录的增量任务；本地已发送列表仍依赖该目录的 IDLE 通知、手动同步或完整对齐。若服务器没有发出通知，本地列表可能延迟显示，但远端 APPEND 成功本身不受这一延迟影响。

当前草稿只保存在本应用的数据目录，不会上传为邮箱服务器的草稿。界面的“发件箱”是本地发送任务；账号下“已发送”是从 IMAP 索引得到的远端目录，两者不能等同。

本次已运行 SMTP 投递边界及中断不重放的既有测试，均通过。未真实发送邮件、连接用户邮箱或读取当前账号私有配置；不能据此断言某个服务商确实自动保存了副本。现有测试也不是 sendJobs 完整 SMTP→APPEND 链路的集成验证，需在实施时补齐。

## 2. 调整目标

1. IDLE 日常事件只更新受影响目录或明确的 UID，不创建全账号完整对齐。
2. 保留手动完整对齐、全历史任务及用户已配置的完整对齐周期；目录增量不改动这些计划。
3. 移动和归档同时覆盖来源、目标；断线期间的新增、删除和标记变化能够补齐。
4. 发送后主动更新已发送目录，不依赖服务器一定发出 IDLE 通知。
5. 可从日志辨认事件、范围、补偿原因与比较结果。
6. 不恢复快速同步轮询，不引入数据库、外部队列或服务商预置逻辑。

## 3. 同步任务分层

| 类型 | 范围与用途 | 更新账号完整对齐时间/计划 |
| --- | --- | --- |
| UID 更新 | 一个目录中的有限 UID，主要更新 flags | 否 |
| 目录新增拉取 | 指定目录已提交水位之后的新 UID | 否 |
| 目录状态核对 | 指定目录的新增 UID、已有本地 UID 的存在性和 flags | 否 |
| 目录重建 | 指定目录 UIDVALIDITY 变化，重建该目录身份与索引 | 否 |
| 目录发现 | 完整 LIST 或明确目标的存在性确认；按需增删监听 | 否，不等同于扫描所有邮件 |
| 账号完整对齐 | 手动、定时 reconcile 或 history，覆盖所有目录 | 成功后更新 LastFull/NextFull |

新增 `delta` 任务表示前四类目录/UID 操作，在任务内记录处理阶段；不把目录任务伪装成账号 reconcile。保留现有 quick 接口作为手动检查新增邮件的入口。

任务新增范围字段，区分 account、folders、uids；范围是执行边界，不只是界面标签。目录任务禁止进入账号级消失目录清理，也不能更新 LastFull、NextFull。仅完整成功覆盖账号全部目录的任务才更新完整对齐状态。

## 4. 事件映射

| 事件 | 处理方式 | 升级边界 |
| --- | --- | --- |
| EXISTS/RECENT | 标记当前目录有新增线索，以已提交 UID 水位获取新增邮件 | 不因消息数量相同就判定无变化；不升级整个账号 |
| UIDNEXT | 与已知目录状态比较，确有推进时拉取该目录新增 UID | 初始 SELECT 的基线信息不当成新的业务变化 |
| FETCH，携带可信 UID 和 FLAGS | 更新同目录、同 UIDVALIDITY 的对应 UID；必要时 UID FETCH 校验 | 不完整或缺少 UID 时仅标记该目录 flags 待核对 |
| FETCH，仅有序号 | 批量 UID FETCH 该目录已有本地 UID 的 flags | 不把序号转换结果直接当作可靠 UID |
| EXPUNGE | 核对该目录本地 UID 是否仍存在，同时检查新增 UID | 序号只作变化线索，不能直接据此删除本地记录 |
| UIDVALIDITY | 比较实际值，变化后使旧代次失效并重建当前目录 | 不影响其他目录；取消旧代次写操作 |
| PERMANENTFLAGS、READ-ONLY、READ-WRITE | 更新目录能力/权限状态；仅在实际变化影响数据时排队目录核对 | 常规状态播报不触发全账号对齐 |
| ALERT/非致命 NO、BAD | 显示脱敏提示，按错误语义处理 | 不仅因警告创建邮件扫描任务 |
| BYE、EOF、超时、IDLE 拒绝或异常提前结束 | 标记该目录离线，关闭并退避重连 | 断开时不立即启动完整对齐；恢复后合并一次目录补偿 |
| 正常 DONE/IDLE 续期 | 保持当前选中目录，收集期间真实事件并继续监听 | 不重置基线，不创建补偿任务 |

事件对象包含 accountID、mailboxID、账号配置修订、监听会话代次、UIDVALIDITY、事件类型、可选 UID/flags、接收时间和原因。协议层在解析时产生不可变副本，不异步读取 IMAP 库中会继续变化的 MailboxStatus 指针。

旧连接、旧账号修订及旧 UIDVALIDITY 的事件一律不能写入新状态。若无法可靠识别 UID，就退到当前目录核对；不维护未经验证的“序号等于 UID”映射。

## 5. 目录增量与删除确认

### 5.1 新增邮件

- 每批捕获当前目录的 UIDVALIDITY 和 UID 上界，从上次成功提交水位之后查询新增 UID；过滤服务器返回的越界 UID。
- 每批最多 FETCH 100 封；沿用内存容量上限及分批事务提交。邮件与水位同事务落盘，失败不得提前推进水位。
- 已建立初始基线的目录，后续新 UID 均作为新发生的目录活动导入，不再按旧 INTERNALDATE 排除。这样旧邮件被移动到目标目录时也能显示。
- “最近 N 天”用于首次补录、历史范围选择及新目录初始化；初始补录完成后记录远端高水位，不用事件拉取从 UID 1 重新补全部历史。此处是对当前 quick 日期过滤的明确调整，需要更新界面说明并回归。

### 5.2 标记与删除

- 已知 UID 的标记更新只处理请求 UID 集合，提交时再次检查目录代次、记录身份和修订；有未完成本地标记操作时保留本地乐观状态，操作完成后再读取确认。
- 缺少 UID 的 flags 事件，以本地已有 UID 集合分批获取 flags，不重新抓取全部信封或正文。
- EXPUNGE 或重连补偿先核对本地已有 UID 的存在性，对确认缺失的候选 UID 再查询确认后删除；不因 FETCH 漏项、超时或部分失败判定删除。
- 单个目录失败只保留该目录的待处理需求，不授权删除其他目录或其记录。
- UIDVALIDITY 变化执行目录重建，按现有规则使旧操作冲突；其他目录的水位、正文缓存与进度不受影响。

## 6. 移动与归档一致性

### 6.1 本地发起的移动

UID MOVE 成功后，记录来源目录的存在性核对，以及目标目录的新增拉取需求；两项需求和本地操作结果在同一事务中持久化。不再请求整个账号 reconcile。

目标目录中的 UID 是新的远端身份，不能沿用来源 UID。若当前协议适配可靠取得 COPYUID 等映射，可用其缩小查询范围；基础实现不依赖此能力，仍通过目标目录水位导入。不能按 Message-ID 全局去重，否则会误删合法副本。

移动成功与目标索引刷新分别展示；目标刷新失败只重试读取，不重放 UID MOVE。重启后恢复未完成的两端读取任务。结果不确定的移动不得自动重放，先核对来源及目标。

### 6.2 其他客户端移动

来源 EXPUNGE 触发来源核对，目标 EXISTS 触发目标新增；二者独立入队并在目录内去重。允许短暂过渡状态，最终来源消失、目标保留。

目标目录尚未被发现、没有监听名额，或服务器未推送对应事件时，由目录发现及既有完整对齐补齐；不宣称标准 IDLE 能保证所有目录结构变化都即时通知。

### 6.3 执行中发生移动

若来源或目标已有任务，事件合并到下一批待处理集合；只有当前任务尚未获取相关阶段快照时才允许吸收新需求。已经捕获上界或完成扫描的任务不得吞掉新事件。

## 7. 连接、启动及重连

1. 启动时每账号合并一次目录发现；对已有目录创建目录级恢复需求。新账号按既有补录范围初始化，不能由每个监听连接各自请求一次全账号任务。
2. 断开仅记录离线代次和待恢复标记。重连成功后，每目录合并一次补偿：新增水位拉取、已有 UID 的 flags 和存在性核对；多次失败不累积多个补偿任务。
3. 不支持 CONDSTORE/QRESYNC 时，离线期间的旧邮件标记无法仅靠新增水位推断，重连需要读取该目录已有 UID 的 flags。这是必要的目录核对，不等同于全账号历史重新导入。
4. 保留 25 分钟续期、10 秒 IDLE/DONE 确认超时及带抖动的指数重连退避；正常续期不走重连补偿。
5. 只有明确认证拒绝才停止自动重试；连接配额、临时不可用及网络错误进入相应退避状态，不能误报密码错误。协议适配尽可能保留结构化响应原因，界面只接收脱敏信息。
6. 暂停、删除、配置更新和服务关闭取消旧代次；新旧代次不能互相清除待处理需求。冻结存储时停止接收可写任务。

### 连接预算

每个选中目录需要单独的 IDLE 连接，不能无限占满服务端连接数，导致发送归档、同步和正文读取无法建立连接。

建议增加每账号统一 IMAP 连接预算，默认总上限 10：IDLE 最多占 7 个，后台操作及正文读取预留 3 个，所有 IMAP 调用统一受预算约束。支持配置上限；已知服务器额度更小时降低预算，并在连接限制错误后保守降低监听覆盖。连接预算并不能推断服务商的真实额度，额度不足仍须明确展示。

优先监听收件箱、已发送、归档和用户当前查看的目录，再覆盖其他目录；没有名额的目录显示“未实时监听”，由手动或既有完整对齐更新，不通过循环轮换 SELECT/NOOP 恢复隐式轮询。设置页显示已监听/可选择目录总数及受限目录，不能只显示成功监听的分母。

## 8. 事件合并、持久化与调度

- 待处理键从账号改为账号 + 目录；保存 newMail、membershipDirty、flagsDirty、reset，以及有限 UID 集合和多项触发原因。
- 保留约 500ms 的事件合并窗口，连续事件最多等待 2 秒后执行一批；UID 集合超过 1000 时降级为该目录 flags/存在性核对，不升级账号级对齐。
- 事件入口可在内存合并，任务入队后用现有 JSONL 持久化范围和进度；重启按目录补偿覆盖尚未持久化的短窗口。移动等已知本地操作的补偿需求须与操作结果同事务持久化。
- 执行时取出不可变批次和版本号，批次之后到来的事件写入新的待处理集合；成功仅清除本批需求，失败保留，不因旧任务完成清除新事件。
- 继续保持同账号写操作/同步阶段串行、全局两个后台账号槽、每片最多 8 步；IDLE 事件处理不能阻塞协议读取线程。
- 手动/定时完整任务只能吸收尚未处理的同范围需求；执行期间新增事件仍须保留。局部 delta 完成不延后账号 NextFull。
- 保留现有持久化修订冲突、容量限制、取消和恢复语义；读取重试不允许触发 SMTP、APPEND 或 MOVE 重放。

## 9. 发送后的配套调整

保留 SMTP 与已发送副本保存的两阶段语义，不因同步优化改变账号的 autoArchive 选择。

1. **客户端保存副本**：APPEND 明确成功后，持久化该 sent 目录的新增拉取需求，主动更新本地列表；没有 IDLE 通知也会执行。无需全账号对齐，基础实现无需引入 UIDPLUS 依赖。
2. **服务器自动保存**：SMTP 成功后对 sent 目录执行一次增量读取，同时继续接受后续 IDLE 通知。服务器异步保存晚于此次读取且没有 IDLE 通知时，仍由后续手动/完整对齐发现，不增加循环读取或自动补 APPEND。
3. **保存状态展示**：autoArchive=true 表示用户选择依赖服务器，当前 archive=server 不是已验证副本。界面应明确“由服务器保存，尚未核实”；能可靠关联到副本后再展示已核实，不因暂时查不到就认为未发送。
4. **未发现 sent 目录**：先进行一次目录发现，再决定能否归档；不自动创建未知名称的目录。若仍无法定位，保留“已发送，副本保存失败”的区分。
5. **不确定结果**：SMTP/APPEND unknown 只允许读取核对，不自动重放。APPEND 已成功而本地索引失败，只重试目录 delta。
6. **明确失败**：保留手动归档重试入口，重试 APPEND 不触发 SMTP 发送。当前归档 unknown 缺少完整人工处理闭环，作为单独后续完善项，不借本次目录同步自动解除不确定状态。

## 10. 日志与前端展示

- 同步设置显示实时监听覆盖、连接限制、最近目录增量及最近账号完整对齐；账号完整对齐的下次计划不随日常事件变化。
- 任务日志继续分两类，每邮箱分别保留最近 5 次终态任务：增量同步包括 quick/delta，完整对齐只包括账号 reconcile/history。进行中和暂停任务保留，局部任务不能挤占完整对齐的日志名额。
- 每任务明确显示“范围：目录/UID/整个账号”、触发原因、目录名称、事件数量、断线补偿代次和新增/更新/删除统计；合并多个事件时保留原因集合及计数。
- 同步过程明细维持最多 200 条，统计累计；不记录协议原文、MIME 或认证信息。旧日志保留原含义，不伪造新范围或新原因。
- 对已读、移动、归档产生的任务，展示受影响目录；不再统一只显示“IDLE 事件触发”。

## 11. 兼容与实施顺序

1. 先增加范围化任务与日志分组，旧任务缺少范围时维持原行为；不原地把运行中的账号完整任务缩成目录任务。
2. 增加不可变事件对象、目录待处理集合及代次校验，再替换日常 IDLE 映射。
3. 接入本地移动的持久化两端补偿、重连目录恢复及新 UID 的补录语义调整。
4. 接入发送后的 sent 目录更新，补充连接预算和状态展示。
5. 完成模拟协议、故障恢复及前端回归后，再按明确部署指令构建和重启。

JSON/JSONL 字段采用可选新增项，不引入数据库。历史账号级任务可完成或按原范围恢复；事件内存状态在启动后重建，已持久化的操作补偿不可丢弃。旧客户端仍能使用 quick/reconcile/history 接口。

## 12. 验收清单

| 场景 | 必须满足 |
| --- | --- |
| 新邮件 EXISTS | 仅查询对应目录新 UID，其他目录无邮件扫描 |
| 单 UID 已读/星标更新 | 仅更新该 UID，不创建账号完整任务 |
| FETCH 无 UID、序号与 UID 不同 | 安全退到当前目录，不错误更新其他邮件 |
| EXPUNGE 同时伴随新邮件 | 两种需求均保留，删除须确认，新 UID 正常导入 |
| 本地移动，服务器不发事件 | 来源移除，目标新 UID 导入，不重放 MOVE |
| 其他客户端移动旧日期邮件 | 目标新 UID 不被初始补录日期过滤丢弃 |
| 扫描中发生移动或标记变化 | 当前快照之后的事件继续执行，不被任务完成清除 |
| 断线、多次失败、重连 | 仅恢复受影响目录，合并补偿；不在断开时扫描整个账号 |
| 正常 IDLE 续期和初始状态播报 | 不产生无变化扫描或重复完整任务 |
| UIDVALIDITY 改变 | 只重建该目录，旧代次写操作和事件失效 |
| 目录新建、改名、NoSelect、删除 | 发现与数据扫描分离；失败不能冒充删除 |
| 连接配额耗尽 | 同步/正文/归档仍受预算保护，受限覆盖明确可见 |
| 新事件连续涌入或服务重启 | 队列有界、能让出执行权，任务与水位恢复正确 |
| SMTP 成功、APPEND 成功且无 IDLE | 远端副本与本地 sent 列表均可验证，SMTP 只发送一次 |
| 服务端自动保存 | 客户端不重复 APPEND；副本显示允许反映服务器异步延迟 |
| APPEND/SMTP 结果不确定 | 不自动重发，不把只读核对变成写请求重放 |
| 单目录 delta 成功 | LastFull/NextFull 不变化，完整日志不被淘汰 |

测试使用本地 TLS IMAP/SMTP 模拟及临时 JSON 数据。验收需要统计实际 LIST/SEARCH/FETCH 访问的目录与 UID 集合，不能只检查任务名称。发送链路需新增完整 SMTP→APPEND→目录 delta 集成测试；不得向真实邮箱发送测试邮件。

## 13. 协议依据与检查入口

- [RFC 2177：IDLE](https://www.rfc-editor.org/rfc/rfc2177.html)：IDLE/DONE、异步通知与周期续期。
- [RFC 9051：IMAP](https://www.rfc-editor.org/rfc/rfc9051.html)：UID/UIDVALIDITY、序号变化、选择目录和 APPEND 语义。
- [RFC 4315：UIDPLUS](https://www.rfc-editor.org/rfc/rfc4315.html)：APPENDUID/COPYUID 等可选定位优化；本方案基础流程不依赖服务器支持。
